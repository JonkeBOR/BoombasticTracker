# Data Model: Fitness Tracker Domain Model

Phase 1 of [plan.md](plan.md). This file describes the stored tables and the domain values. The
Drizzle schema in `src/features/fitness-tracker/server/schema.ts` is the single source of truth.
Rule numbers refer to [domain-spec.md](../../domain-spec.md) and FR numbers to [spec.md](spec.md).

## Conventions

- **IDs**: `text` UUIDs generated by the app (research R7).
- **Instants**: `integer` epoch milliseconds, mapped to `Date` by Drizzle (`mode: 'timestamp_ms'`).
- **Weights**: `integer` grams. The domain and API use kilograms.
- **Ordering**: a `position` integer, 1…n, contiguous within its parent. Operations renumber after
  every insert, remove or move.
- **Scope**: every root table has `profile_id`, and every query filters by it (FR-001, SC-007).
  Child tables reach the profile through their parent.

## Aggregates

| Aggregate (root) | Tables                                                                                | Changed by                                                         |
| ---------------- | ------------------------------------------------------------------------------------- | ------------------------------------------------------------------ |
| Profile          | `profiles`                                                                            | activation operations                                              |
| Exercise         | `exercises`                                                                           | catalog operations                                                 |
| Program          | `programs`, `training_blocks`, `workouts`, `exercise_slots`, `planned_sets`, `cycles` | program edits, activation, progression, logging (last weight only) |
| Workout session  | `workout_sessions`                                                                    | start and finish workout, cycle end                                |
| Set log          | `set_logs`                                                                            | insert only                                                        |
| Bodyweight entry | `bodyweight_entries`                                                                  | insert only                                                        |

A spec **block prescription** is not a table. It is the set of `planned_sets` rows for one
`(exercise_slot_id, training_block_id)`. "Exactly one prescription per block" (FR-010) is satisfied
by construction. "One or more planned sets" (FR-011) is checked by the activation rule (FR-017) and
kept by the default for new blocks (R10).

## Last weight

- Set when a planned set is logged: the planned set's last weight becomes the logged weight, and an
  unweighted log sets it to null (rule 15, spec Assumptions). It goes in the same batch as the set
  log insert.
- Unchanged by skipping (rule 11), by finishing a session, and by any cycle transition.
- Cleared for **all** of a slot's planned sets in every block when the slot's exercise is replaced
  (rule 18).
- Null on every planned set that is created later: new set numbers, blocks or slots (rule 19, R10).
- Kept when a set's target changes or the block or slot is moved (R9, R10).

## State transitions

### Cycle

```text
           start (activation, start over, or previous cycle completed)
                 │
                 ▼
            ┌─────────┐  last block complete     ┌───────────┐
            │ active  │ ───────────────────────▶ │ completed │ ──▶ new cycle n+1 at block 1
            └─────────┘                          └───────────┘
              │     ▲ current block complete:
              │     └─ current_block_number += 1
              │
              │ start over (rule 8) ──────────▶ ended_early ──▶ new cycle n+1 at block 1
              │ pause or another program activated (rule 2) ──▶ ended_early (no new cycle)
```

Leaving `active` for any reason sets `ended_at` and closes that cycle's `in_progress` sessions as
`finished` (rule 13). All of this happens in the same batch.

### Workout session

```text
start workout ──▶ in_progress ──finish workout / cycle ends──▶ finished
      ▲               │
      └── resume ◀────┘   (starting the same workout again in the same cycle-block)
```

Sets can be logged only while `in_progress`, and only when the session's cycle is the program's
active cycle. Starting a workout that already has a `finished` session in this cycle-block is
refused (rule 10).

## Derived, never stored

- **Block complete**: every current workout of the program has a `finished` session for
  `(cycle_id, block_number)` (rule 6). A program with zero workouts never completes a block;
  activation refuses it anyway (FR-017).
- **Suggested next workout**: the first workout in `position` order without a `finished` session in
  the current cycle-block (rule 10).
- **Prefill**: `planned_sets.last_weight_grams` for the session's slot × block (rule 14).
- **Weigh-in available**: no `bodyweight_entries` row for `(profile_id, today in time zone)`
  (rule 22).
- **Exercise history**: `set_logs` for one exercise, optionally grouped by
  `(training_block_id, block_number)` across `cycle_number` (FR-035).
